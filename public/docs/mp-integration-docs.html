⚠️ Separación de responsabilidades: Las claves secretas (MP_CLIENT_SECRET, MP_ACCESS_TOKEN, MP_WEBHOOK_SECRET) viven solo en Supabase Secrets y nunca llegan al browser. Las claves públicas (VITE_MP_PUBLIC_KEY_*) están en el frontend y es seguro que así sea — MP las diseñó para eso.

💳 Flujo de pago completo

Flujo principal — paciente agenda y paga

1
Selección de profesional El paciente elige clínica → especialidad → profesional → fecha/hora en /paciente/reservar
2
PaymentPage — carga configuración MP El frontend llama a mpService.getPaymentPlatformConfig() → Edge Function mp-save-card retorna la public key correcta según MP_IS_PROD. Si no hay public key, entra en "modo demo" (badge amarillo).
3
Selección o tokenización de tarjeta El componente SavedCardSelector muestra tarjetas guardadas del paciente. Si no tiene, renderiza MercadoPago Checkout Bricks para ingresar una tarjeta nueva — los datos nunca pasan por nuestros servidores, MP los tokeniza directamente.
4
Crear consulta (status: pending) Antes de cobrar, se crea la consulta en Supabase con status: 'pending' y payment_status: 'pending_payment'. El DB write ocurre ANTES de intentar el pago — si algo falla, queda registro.
5
Cobro vía Edge Function mp-payment El frontend envía { consultationId, amount, cardId, professionalId } → Edge Function usa MP_ACCESS_TOKEN para hacer POST /v1/payments a la API de MP. El token de tarjeta nunca llega al browser.
6
Resultado del pago Si status === 'approved' → redirige a /paciente/turno-confirmado/:id. Si falla → toast de error, la consulta queda en pending_payment para reintento.
7
Webhook confirma en backend MP envía una notificación a /functions/v1/mp-webhook. La Edge Function verifica la firma HMAC con MP_WEBHOOK_SECRET y actualiza el estado de la consulta en Supabase.

🗂️ Cuándo se usan las tarjetas guardadas

Primera vez que paga

El componente SavedCardSelector no tiene tarjetas para mostrar → renderiza Checkout Bricks de MP: formulario completo con número, vencimiento, CVV y nombre del titular.


El paciente puede tildar "Guardar tarjeta para futuras compras" → MP retorna un customer_id y un card_id que guardamos en Supabase (tabla patient_payment_methods).

Pagos siguientes

El componente consulta las tarjetas guardadas del paciente (mpService.getSavedCards(patientId)) y las muestra como chips seleccionables con últimos 4 dígitos + icono de red.


El paciente elige una → el frontend envía solo el card_id a la Edge Function → MP procesa sin volver a pedir datos de la tarjeta.

Datos que guardamos de las tarjetas

CampoGuardado enPara qué sirve
mp_customer_id profiles del paciente ID de cliente en MP — necesario para listar y cobrar tarjetas guardadas
card_id patient_payment_methods Token de la tarjeta en MP. Se envía al cobrar — MP conoce los datos reales
last_four_digits patient_payment_methods Para mostrar al paciente cuál tarjeta es (ej: "•••• 4242")
payment_method_id patient_payment_methods Red de la tarjeta (visa, mastercard, etc.) — para mostrar el logo
expiration_month/year patient_payment_methods Mostrar vencimiento + alertar si expiró
Nunca guardamos: el número completo de tarjeta, CVV, ni ningún dato sensible de PCI. Solo los tokens que MP nos devuelve, que son inútiles sin las credenciales del merchant.

⚡ Edge Functions de MercadoPago

FunciónEndpointQué hace
mp-connect OAuth callback Maneja el flujo OAuth cuando un profesional conecta su cuenta MP propia. Guarda el access_token del profesional para pagarle directamente (split de pagos futuro).
mp-save-card POST /mp-save-card Guarda una nueva tarjeta del paciente en MP (crea customer_id si no existe) y registra el card_id en Supabase. También expone GET /mp-save-card?action=config para devolver la public key al frontend.
mp-payment POST /mp-payment Procesa el cobro. Recibe consultationId + cardId + amount, llama a MP API con el access token del servidor, y actualiza el estado de la consulta según resultado.
mp-webhook POST /mp-webhook Recibe notificaciones de MP (pagos, vinculaciones OAuth). Verifica firma HMAC con MP_WEBHOOK_SECRET. Actualiza consultations.payment_status y dispara notificaciones push.

🔔 Webhook — cómo funciona

URL registrada

https://aixjejdoofervrkggbkd.supabase.co/functions/v1/mp-webhook


Registrada en MP Developer Portal para Modo de prueba y Modo productivo. La misma URL atiende ambos — el flag MP_IS_PROD en la Edge Function determina cómo se procesa.

Eventos que escucha
  • Vinculación de aplicaciones
    Cuando un profesional conecta su cuenta MP. Dispara el flujo OAuth de mp-connect.
  • Pagos (legacy)
    Notificación de cada pago procesado. Actualiza payment_status en Supabase y notifica al profesional.
Verificación de firma HMAC

Cada notificación de MP llega con el header x-signature. La Edge Function verifica que el cuerpo del request fue firmado con MP_WEBHOOK_SECRET antes de procesar — esto previene que alguien malicioso envíe requests falsos al webhook.

// Verificación en mp-webhook/index.ts
const signature = req.headers.get('x-signature')
const isValid = await verifyHmac(body, signature, MP_WEBHOOK_SECRET)
if (!isValid) return new Response('Unauthorized', { status: 401 })

🚦 Feature flag IS_PROD

El flag controla todo el ambiente. Cuando es false, todos los pagos usan la infraestructura de testing de MP (sin dinero real). Cuando pasa a true, todo el tráfico va a producción.

VariableUbicaciónEfecto
MP_IS_PROD=false/true Supabase Secrets Edge Functions usan credenciales sandbox o prod para cobrar y verificar webhooks
VITE_MP_IS_PROD=false/true Vercel Environment Variables Frontend inicializa Checkout Bricks con la public key sandbox o prod
Cómo funciona el frontend: mpService.getPaymentPlatformConfig() llama a la Edge Function que lee MP_IS_PROD y retorna { publicKey: "TEST-..." } o { publicKey: "APP_USR-..." }. Si la respuesta no tiene public key, PaymentPage.jsx muestra el badge "DEMO" y bypasea el pago real.

🎭 Modo Demo

Cuándo activa

Cuando getPaymentPlatformConfig() no devuelve una public key (Edge Function caída, credenciales no configuradas, o en desarrollo sin Supabase). El componente detecta esto con:

const isDemoMode = !configLoading && !publicKey
Qué muestra
  • Badge "DEMO" en amarillo en la sección "Método de Pago"
  • Tarjeta "Pago de demostración — Sin cargo real" pre-seleccionada
  • Botón primario "Confirmar y Pagar" que crea la consulta con payment_status: 'demo'
  • Botón secundario "Avanzar (demo)" para testing rápido del flujo post-pago
En modo demo se crea la consulta en la DB igual que en modo real, para que el flujo post-booking funcione completo. La diferencia es que payment_status queda como 'demo' en lugar de 'paid'.
