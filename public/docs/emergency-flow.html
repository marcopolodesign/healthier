Triage — selección múltiple sin severidad visible

Desde el cambio de hoy (2026-08-03), la pantalla de triage muestra una lista plana de síntomas (src/data/emergencySymptoms.js) sin agrupar por color y sin badge en vivo — a pedido explícito de Mateo, para no influenciar la selección del paciente. El código de triage se sigue calculando igual (computeTriageCode: gana la severidad más alta tildada, ROJO > AMARILLO > VERDE) pero recién se muestra en la pantalla de Confirmar. Los labels de los síntomas elegidos se guardan como JSON en emergencies.notes y son lo que ve el profesional al llegar.

2. Vista del Profesional + Super-admin (Website)

El profesional atiende desde src/pages/professional/Emergencias.jsx, montada en /profesional/emergencias — es una ruta standalone, registrada antes del bloque AppLayout en App.jsx (sin sidebar, mobile-first, para usarse en la calle). El super-admin supervisa todo desde /super-admin/emergencias y configura precio/disponibilidad desde /super-admin/verticales.

Mecanismo realtime: emergencyService.subscribe(professionalId, onChange) abre un canal Supabase Realtime filtrado por professional_id, escuchando INSERT y UPDATE sobre emergencies (canal activo recién desde la migración 086 — antes la tabla no estaba en la publicación supabase_realtime y estas suscripciones eran código muerto). En paralelo, cada dispatch dispara un push real vía la Edge Function send-push-notification — es el canal de respaldo cuando el browser del profesional está cerrado; la suscripción realtime sola sólo funciona con la pestaña abierta.
Modo demo (solo dev): ?demo=dispatched|in_transit|arrived inyecta datos fixture para previsualizar cada fase — gateado detrás de import.meta.env.DEV, así que en producción el parámetro se ignora por completo y siempre corre el camino real contra la DB.
Super-admin: /super-admin/emergencias lista todas las emergencias (badge de triage, estado, paciente, profesional, ubicación con link a Maps, precio) vía la policy RLS emergency_super_admin_select. El precio y la disponibilidad del servicio se configuran en /super-admin/verticales, sección "Servicio de emergencias" — regla de visibilidad del proyecto: toda capacidad operativa nueva tiene que verse desde el panel de super-admin.

5. TODOs y gaps conocidos

🟡 Cobro real del S.O.S: hoy se registra price_at_request y payment_method_id al despachar, pero nunca se ejecuta un cobro — el Edge Function mp-payment está atado a un consultationId (ver createPayment({ consultationId, ... }) en mpService.js) y una emergencia no crea una consultation. Falta decidir si se cobra al cerrar (completed) generando una consulta asociada, o se extiende mp-payment para aceptar emergencyId directamente.
🟢 Unicidad del dispatch code: UTM-#### se genera en el cliente con Math.random(), sin constraint UNIQUE ni verificación server-side. Con el volumen actual (un profesional, MVP pre-lanzamiento) la probabilidad de colisión es irrelevante, pero no está garantizada.
🟡 Link emergencia → historia clínica: clinical_encounters.encounter_type ya admite 'emergency' (migración 033) pero nadie lo usa — al día de hoy cerrar una emergencia no crea ni vincula un clinical_encounter, así que la atención de S.O.S. no queda registrada en la historia clínica del paciente.
🔴 Paridad mobile: la regla "nada de mobile" (2026-07-27) está vigente y suspende la Feature Parity Rule del proyecto. Si se retoma mobile/, su flujo de S.O.S sigue siendo el viejo mockeado: pago simulado (setTimeout), GPS fake, arrived disparado por timer en vez de estado real. Portar el flujo real de website (triage plano, dispatch aleatorio, realtime, push) implica reescribirlo entero, no ajustarlo.
🟢 Camino "sin profesionales disponibles" sin ejercitar E2E: el código maneja el caso ({ noProfessional: true }, sin INSERT) pero con un solo profesional medicina_general on-demand en el pool no se prueba naturalmente — requiere desactivarlo a propósito para validar la pantalla honesta.
🟡 WhatsApp como canal de respaldo: TODO histórico documentado en emergencyService.js — la suscripción Realtime sólo entrega si el browser del profesional está abierto; el push de send-push-notification ya cubre el caso de app/tab cerrada, pero requiere que el profesional haya aceptado la suscripción push del browser. WhatsApp (Twilio o Meta Cloud API, disparado desde un Edge Function on INSERT) quedaría como un tercer canal de respaldo sobre ese caso.
